# 防災施設コンソール UI/UX改善提案書

作成日：2026-09-09  
対象：`disaster_prevention_demo`（`disaster_prevention_demo02`は対象外）  
評価方法：既存要件・全8画面のソースレビュー、大手SaaSの公式デザイン資料との比較  
ステータス：**操作・信頼性の提案版。** ブラウザ実機（1280×900）での「描写の作り込み」は [06_描写と作り込みの改善提案.md](06_描写と作り込みの改善提案.md) に分けた。体育館版は `disaster_prevention_demo02/docs/05_描写と作り込みの改善提案.md`。

## 1. 提案の結論

大手SaaSと比較できる品質に近づけるには、配色の刷新より先に、**「施設を探す → 根拠を確認する → 対応を記録する → 書類で説明する」までを一続きにする**ことが必要である。

現在の実装には、明るい共通シェル、4段階の判定、平常／災害時の切替、写真と点検記録を同じ施設に集める構成がある。この軸は残す。一方、検索のない一覧、操作できない推奨アクション、修正できない画像判定、施設を切り替えられない書類など、閲覧の先で作業が止まる箇所がある。

推奨順序は次のとおり。

1. **P0：操作の一貫性と信頼性** — 施設の文脈を維持し、判定の保存範囲・訂正・根拠を明示する。
2. **P1：日常業務の速さと見た目の完成度** — 検索、絞り込み、作業キュー、詳細パネル、情報階層を整える。
3. **P2：利用環境の拡張** — タブレット・スマートフォン、実印刷、実データ接続を段階的に追加する。

「大手並み」は見た目の主観点数では認定しない。第10章の操作シナリオと品質基準を満たし、実画面で検証した段階を完成条件とする。本書は防災上の開設判断の妥当性を認定するものではなく、その根拠と人の判断を扱うUIの提案である。

## 2. 調査範囲と確認の限界

### 実施できたこと

- LP、ダッシュボード、施設一覧、インシデント、画像確認、書類、システム連携、AIアシスタントの実装を確認。
- `app/globals.css`、共通シェル、画像表示、画像確認の状態管理を確認。
- 既存のテーマ別要件定義書・UIUXデザイン要件と照合。
- Atlassian、Salesforce、IBMの公式資料とW3Cのダイアログ設計資料を参照。

### ブラウザ確認の実施状況

ブラウザ接続状態の取得結果は `browsers: []`。Chromeで `http://localhost:3000` を開く試行は `Browser is not available: chrome`、内蔵ブラウザも `Browser is not available: iab` で停止した。これはブラウザ接続環境の制約であり、アプリが起動しないことを示すものではない。ポート3000での稼働も確認できていない。

したがって、スクリーンショット、実際の表示崩れ、クリック結果、ブラウザの戻る操作、フォーカス移動、コンソールエラー、表示速度は未検証。本書で「実装確認」と書く箇所はコードに基づく事実であり、「実画面確認済み」を意味しない。第10章を実行してから最終監査版に更新する。

## 3. 比較する大手SaaSの品質軸

製品の契約画面へログインして横並び評価したものではない。公開された公式の設計原則・コンポーネントを比較基準にしている。IBM Carbonは企業向けUIの補助基準として扱う。

| 比較対象・公式根拠 | 参考になる品質 | 本デモへの適用案 |
|---|---|---|
| [Atlassian Dynamic table](https://atlassian.design/components/dynamic-table) | 表のソート・ページ分割など、データを扱う操作が標準化されている | 施設検索、状態フィルター、件数、解除操作を一覧の上部に集約。22件の現状ではページ分割は急がない |
| [Salesforce：反復可能な設計パターン](https://www.salesforce.com/blog/repeatable-design-patterns/) | 共通のレコード画面によって操作を覚え直す負担を減らす | どの施設も同じ詳細構造にし、概要・点検・画像・書類を施設IDでつなぐ |
| [IBM Carbon：Empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/) | データがない場面にも状況説明と次の手段を設計する | 記録なし、検索結果なし、画像取得失敗を別の状態として表示する |
| [W3C APG：Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | ダイアログのフォーカス管理・キーボード操作 | 詳細パネルの初期フォーカス、Tab循環、Esc、閉じた後の復帰を設計する |

これらから導く本提案の判断は、**コンポーネントの美しさと、検索・訂正・復帰・例外状態の一貫性を同じ優先度で扱う**というもの。大手製品の機能数や画面密度をそのまま移植する必要はない。

## 4. 現状の強みと主要な差分

### 残すべき設計

- 白系の背景と抑制した状態色。危機管理センター風の暗色・全面警告色には変更しない。
- 平常と災害時で同じ施設を比較する構造。切替だけで並び順を変えない。
- 「確認できていない」を独立した判定として残し、未記録を正常扱いしない。

- 共通ナビ、状態ピル、44px以上の標準ボタン、フォーカスリング、モーション軽減の土台。

## 5. 目指す情報設計と主要フロー

### 5.1 施設を共通の軸にする

施設詳細に「概要／点検記録／関連画像／対応履歴／書類」を配置する。初期表示は概要と次の確認事項だけに絞り、詳細はタブや展開で見る。市庁舎も同じ詳細構造にするが、「指定避難所ではない」を明示し、避難所収容人数の集計に入れない。

URL案：`/console/facilities?view=shelter&facility=F01&status=conditional`。検索語やフィルターはURLで保持し、詳細を閉じる・ブラウザで戻ると元の一覧に復帰する。切替時に保持する項目と解除する項目を決め、解除した条件は表示する。

### 5.2 主役にする体験

```text
ダッシュボード「確認できていない 3施設」
  → 災害時一覧（未確認に絞り込み）
  → 施設詳細（不足記録・最終確認日・確認先）
  → 確認内容を記録（デモ保存）
  → 対応履歴に反映／未確認の開設判定は勝手に変えない

総合体育館の条件付き判定
  → インシデントの結論・残条件
  → 写真と点検記録を確認
  → 対応状況を記録
  → 開設記録の下書きで根拠と残条件を確認
```

写真の「問題なし」と、施設の「開設可能」は別の判断である。写真判定だけで施設を使える状態に変えない。人による記録、対応完了、開設判断を別の状態としてモデル化する。

## 6. 画面ごとの改善仕様

### ダッシュボード

最上部に「指定避難所21施設の判定」と基準日時を表示し、施設一覧22件との差を説明する。既存の12／4／2／3と2,385人は維持し、数値に「施設」「人」を付ける。

4枚の指標の直下に「次に確認すること」を配置。総合体育館の残条件と未確認施設への入口を出す。画像未確認件数と施設未確認件数は別物としてラベルを分け、根拠なく合計しない。模式地図と連携状況はこの下に置く。

### 施設一覧・詳細

一覧上部を「平常／災害時」「施設を検索」「状態」「該当件数」「解除」で統一。標準順序は維持し、任意の並べ替えはP1の後半とする。切替による自動ソートは行わない。

先頭列とヘッダーを固定し、長い理由は2行程度＋詳細に収める。「—」だけで不明を表さず、記録なし・対象外・未確認をデータとして区別する。データに区別の根拠がない場合は推測で補完しない。

詳細パネルは幅480〜560pxを初期案とし、施設名、判定、理由、記録日時、確認事項、書類へのリンクの順に並べる。元の一覧幅と両立しない画面では全画面の詳細に切り替える。

### インシデント

冒頭に施設名、条件付き判定、残っている条件を要約する。左を写真・点検の証拠、右を判断と対応に分ける。右側はデスクトップで追従表示を検討し、長い写真列の下までスクロールしても対応操作に戻れるようにする。

相関81%は大きな成果指標として強調しない。「同じ施設に関する情報の関連付け・デモ値」という意味を近くに表示し、開設可否の確率と混同させない。根拠情報と推奨事項を視覚的に分ける。

各アクションに「未着手／確認中／確認済み」、記録者、記録日時、メモを持たせる。外部への連絡送信は追加せず、デモ内の記録で業務のつながりを見せる。

### 画像確認

未確認を優先して見せ、確認済みは履歴として残す。写真拡大、撮影日時、施設・場所、参照ナレッジを同じカードにまとめる。ナレッジIDは参照内容を開けるリンクにする。

判定後は「対応が必要として記録しました」＋取り消しを表示し、履歴からいつでも訂正できるようにする。行の移動後にフォーカスが失われないことを検証する。保留は「確認待ち」として残し、未確認を無理に二択で処理しない。

### 書類

施設セレクター、施設名、下書き状態、基準日時を先頭に配置。点検記録から転記した欄と、職員の確認が必要な欄を区別する。各値から元記録へ戻れるようにする。

狭い画面では帳票2枚をタブで切り替える。空欄を見栄えのために埋めない。PDF生成はP2とし、P0では画面内の整合性と参照元への移動を完成させる。

### システム連携

5／8は維持し、単なる進捗率より「どの施設のどの判断に不足が影響するか」を示す。各行に最終同期日時・取得対象・担当を追加する場合、モック値であることを明示する。未確認には詳細を確認する入口を用意する。

CSS上、`.goal`の負のtopと親の`overflow:hidden`が組み合わされているため、100%ラベルはクリップの可能性がある。実画面で確認し、必要ならバー外の兄弟要素に移す。

### AIアシスタント

先頭に「デモの記録に基づく定型回答」と表示。主役は質問候補と回答根拠にする。自由入力の未対応時には「このデモで確認できる質問」を案内し、無関係なインシデントリンクを付けない。

回答は結論、対象施設、根拠・基準日時、詳細リンクの順に構成。入力欄は画面下部に維持し、会話が伸びても利用できるようにする。最新回答は読み上げ対象にし、空入力時は送信不可にする。AI APIは追加しない。

### LP

既存の見出しと写真の方向性は維持する。施設一覧の切替が価値の中心なので、写真に加えて実際のコンソールのプレビューを候補とする。スクリーンショットはブラウザ接続後に取得し、未実装画面を完成済みとして見せない。

主CTAは「コンソールを開く」、副CTAは「施設一覧の切替を見る」を推奨。AIはコンソール内で文脈とともに触れる導線へ寄せる。ファーストビューには対象、できること、デモであること、約2分の体験を収める。

## 7. 見た目を仕上げる共通仕様

既存の色トークンと4pxグリッドを基礎にし、以下は実画面で調整する初期値とする。

| 項目 | 推奨仕様 | 狙い |
|---|---|---|
| シェル | ヘッダー64〜72px、ナビ216〜232px、本文余白24〜32px | ナビ・業務内容・全体状態の区分を安定させる |
| 文字 | 本文14px、補助12〜13px、見出し22〜24px、指標32px | 同じ役割を同じ大きさにする |
| 太さ | 本文400、操作・見出し500〜600、数字は等幅 | 大きさだけに頼らず情報階層を出す |
| 操作 | 主操作は領域ごとに1つ、通常44px高、重要な状態に単位を付ける | 押す場所と結果を明確にする |
| 色 | 通常の主操作は濃いink、AI専用アクセントは紫、警告は薄地＋濃い文字 | 色の意味を統一する |
| 選択 | ナビに背景と左マーカー、フィルターに選択チップ | 選択状態を白背景だけに依存させない |
| カード | 12px角丸、16〜20px内余白、影は浮くパネル中心 | 全要素を同じ強さで囲わない |
| 表 | 52px程度の基本行、ヘッダー・先頭列固定、表内スクロール | 対象施設を見失いにくくする |
| 状態 | hover／focus／selected／disabled／loading／empty／errorを共通化 | 正常時以外も作り込む |

1280px・1440pxではページ全体の横スクロールをなくすことをP1の目標にする。1024pxはナビ縮小と2列の縦積み、390pxは施設詳細・画像確認の現場利用をP2で設計する。表の二次元性が必要な部分だけ横スクロールを許容する。

| 段階 | 内容 | 主な変更先 | 概算 | 完了条件 |

| 0 | ブラウザ監査、比較用キャプチャ、仕様確定 | 本書と03要件書 | 1〜2人日 | 第10章の現状結果と画像を取得 |
| P0 | 共通施設詳細、キーボード、判定訂正、共通状態、帳票の施設選択、デモ日時 | `ConsoleShell`、`FacilitiesView`、`ReviewState`、`ReviewView`、documents、incident | 5〜8人日 | 主要フローが途切れず、変更・訂正が関連画面で一致 |

P0〜仕上げは合計12〜20人日、事前監査込みで13〜22人日が目安。主に画像確認・対応履歴・書類の共有状態の設計が見積もりを左右する。まずP0を完成させてから装飾の細部を調整する。

共通化候補はPageHeader、FilterBar、FacilityDetail、EvidenceLink、EmptyState、SaveNotice。CSSの一括置換より、施設詳細と状態表示から順に揃える。デモ保存にはバージョン付きsessionStorageなどを使い、初期データへ戻す操作を用意する。実運用の永続化と混同させない。

## 10. ブラウザ確認と完成判定

**以下はすべて未実施の検証計画。現時点で合格とした項目はない。** ブラウザ接続と対象アプリの実際のURLを確認できた環境で実行する。

| シナリオ | 操作 | 合格基準 |
|---|---|---|
| LP→業務開始 | CTAからダッシュボードへ進む | デモと分かり、主操作に迷わず到達 |
| 概況→対象 | 未確認カードを開く | 未確認3施設の一覧となり、フィルターが見える |
| 平常→災害時 | 同じ施設一覧で2回切り替える | 施設順・対象が維持され、期限と判定の違いが分かる |
| 検索→詳細→復帰 | 施設検索、詳細、閉じる、ブラウザで戻る | 検索・位置・フォーカスが適切に復帰 |
| 地図→施設 | 総合体育館以外のピンを開く | 押した施設が選択済みで表示される |
| 根拠→対応 | インシデントから写真・記録、対応記録へ進む | 根拠と確認操作が結びつき、状態と日時が見える |
| 判定→訂正 | 白バンを「対応が必要」、取り消し、再判定 | 件数・履歴が整合。行移動でフォーカスを失わない |
| 再読込 | 判定記録後に再読込 | 宣言した保存範囲のとおりに復元される |
| 記録→書類 | 施設を変えて下書きを開く | 施設・根拠・残条件が一致し、未記録が正常で埋まらない |
| AI | 定型3問、未知の質問、空入力、長い会話 | 正しい案内と根拠リンク。入力欄が利用可能 |
| キーボード | Tab、Shift+Tab、Enter、Escで主要フローを操作 | 施設を開ける、パネル内で移動できる、閉じて復帰できる |
| 例外 | 0件検索、画像取得失敗、保存失敗を模擬 | 状況と次の手段が表示され、入力や文脈を失わない |

### 表示・品質の検証条件

- ChromeとEdgeで1280×800、1440×900を確認。P2では1024×768と390×844を追加。
- ダッシュボード、一覧の両モード、詳細、インシデント、判定前後、書類、AIをキャプチャする。
- 本文のコントラスト4.5:1を設計目標にし、色の実測値で確認。対象コンポーネントだけの確認で全体の規格適合を宣言しない。
- 200%拡大で主要操作が欠けない。キーボードと読み上げで主要フローを確認する。
- 画像のトリミングと検出枠の位置、相関ノードの重なり、サイドバー下部のデモ注記、表の長文折返しを実測する。
- consoleの未処理エラー、画像404、主要リンクの行き止まりが0件。
- 読込性能は対象端末・接続条件を記録して測定する。現時点の性能値やLighthouse点数は未取得。

### 利用者テストの目標

対象業務に近い利用者5名程度による形成的テストを提案する。統計的な優位性を証明する人数ではない。現状版と改善版で同じタスクを実施し、操作時間・迷った箇所・誤解を比較する。

- 5名中4名以上が説明なしで対象施設の未確認理由に到達する。
- 対象施設の検索から根拠表示まで30秒以内を初期目標にする。
- 判定の訂正を自力で完了できる。
- 「記録なし＝使える」「画像確認済み＝開設済み」という誤解が0件。
- デモ全体を約2分で説明でき、最後に書類と根拠のつながりが伝わる。
